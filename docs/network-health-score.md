# 网络健康评分 v1

入口：`/health`（中英文、站点选择、手动刷新），`GET /api/health/score?site=lab`。完整运维视图和中英文 Grafana 汇报均加入健康卡片、设备分数及明细入口。Prometheus 保存 `aiops_health_score`、`aiops_health_coverage_percent`、`aiops_health_deduction_points` 和 `aiops_health_unassessed_points`，标签为设备和站点。

这是一套**可解释的初始运维评分规则**，不是行业认证标准、业务 SLA、连通性测试或安全合规评分。只读取现有正常采集结果和拓扑快照，不主动登录或探测设备。首轮采集未完成时覆盖率较低；全部无有效证据时 API 总分为 null。

| 检查项 | 基础权重 | 规则 |
|---|---:|---|
| 采集可用性 | 40 | 本轮采集成功 100，失败 0；失败不直接断言设备离线 |
| 已确认链路端口 | 20 | 已确认物理线缆的端口，oper up=100、down=0；管理员关闭的口排除。无确认连线或无有效接口数据记缺证 |
| CPU / 内存 | 各 10 | 利用率 ≤70%=100 分；80%=80、90%=50、95%=20、100%=0，中间线性插值 |
| BGP / OSPF / Overlay | 5 / 3 / 2 | 已观察邻居正常=100、异常=0；BGP 按设备内邻居＋VRF 去重；OSPF 2-Way 不误判为 down |
| 电源 / 模块 | 各 5 | 明确正常=100、明确异常=0；仅 present、unknown 或未识别标签不作为健康证据 |

每项先平均其观察对象，再加权；设备等权平均得到所选范围总分。CPU/内存为当前采样，尚不做持续时间或迟滞判定。端口累计 errors/discards 不直接扣分，因为它们可能是很早之前发生的错误。未接线的空闲口不计入接口评分。

**缺证与扣分分别计账：**

- `健康评估分 = 100 × Σ(适用权重 × 已证实健康比例) / Σ适用权重`。
- `证据覆盖率 = 100 × Σ(适用权重 × 可判定比例) / Σ适用权重`。
- 总分＋已观察问题扣分＋缺证暂未获得分数＝100（显示时可能有舍入差）。例如没有故障证据但缺少 20% 证据时，得到 80 分、覆盖率 80%、故障扣分 0、缺证 20 分；不能把这 20 分解释成设备故障。
- 保留 `observed_score` 仅辅助排查，它对已观察部分归一化，不能替代包含缺证的总分。
- 未采集的平台能力、明确不适用的电源占位项、成功返回但没有观察到邻居的协议项会排除并重新分配权重；明细明确列出排除原因。不把失败命令当成不适用。
- 空邻居表不证明协议配置正确；v1 尚无“预期邻居”基线，无法发现已从配置/表中消失的邻居。不同平台的排除范围可能不同，应连同明细比较分数。
- 每次 API/Prometheus 请求重新检查时效（默认 600 秒）。陈旧数据或失败数据集不获得健康分。全部数据缺失时总分未知；设备 Prometheus 分数为 0、覆盖率为 0，表示未获得任何可验证分数，不是已确认故障。

Grafana 90–100 绿色、80–90 黄色、60–80 橙色、低于 60 红色，仅供初步分流；颜色也可能由缺证造成，必须结合覆盖率和明细。Agent 不可抓取时卡片不沿用“健康”判断。Grafana 卡片依时间选择显示对应时间的样本，详情页只展示当前状态。

尚未纳入：探测时延/丢包、带宽饱和、CRC/丢弃增量、持续资源压力、预期协议邻居基线、业务探测、安全威胁与实际报文转发。后续扩展应先补齐可靠采集和基线，再增加维度，不能从缺失指标推断正常。
